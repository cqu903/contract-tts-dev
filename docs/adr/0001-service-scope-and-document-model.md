# 对外粤语合同 TTS 服务的定位与文档模型

> **后续修正**：ADR-0005 把 `contract_id` 改为 `sha256(原文 + template_id)`；ADR-0006 把音频缓存键改为 `sha256(归一化文本 + 引擎)`（音色不入键）。本 ADR 正文保留原始表述。

将本服务从「服务端预注册、只读的可行性探针」转为真实对外服务时，界定其范围与文档模型：

- **范围收窄为合同**：服务只处理香港贷款 / 金融合同 TXT，不处理普通文档。合同的归一化（金额 / 日期 / 身份证 / 罗马序号 → 粤语读法）与切片调参高度专用，普通文档与之差异过大，收窄可避免为不存在的通用性买单。
- **文档模型 = 有状态、内容寻址**：调用方 `POST` 上传合同 TXT，服务以 `contract_id = sha256(原文)` 引用并临时持久化原文。同一原文 → 同一 contract_id → 同一确定性分段 → 同一段序，使 seek 稳定、且与现有内容寻址音频缓存（`sha256(归一化文本 + 音色)`）一脉相承。
- **朗读维度由服务全权决定**：音色、引擎（本地 GPT-SoVITS / 云端 CosyVoice）、语言均由服务端裁定，调用方不可指定；调用方只决定「读什么」——即合同 TXT 及其模板类型 `template_id`（见 ADR-0005）；该模板具体的分段与归一化实现也由服务裁定。这把「怎么读」的质量风险隔离在服务内部，对外接口签名因此不含 voice / engine 参数。

## 考虑并否决的方案

- **通用文档 TTS**：否决——普通文档与合同的归一化差异过大，通用化会稀释合同专项能力。
- **无状态（每次请求带全文）/ 有状态随机 UUID**：否决——前者每次重传原文、且 GET 音频端点带全文不雅；后者丢掉内容去重，与现有内容寻址缓存割裂。
- **调用方可选音色 / 引擎**：否决——引入音色治理、按音色计费、缓存与播放清单多分支。v1 每个引擎只用一个审定粤语音色；音色是引擎内部固定属性（ADR-0006），不暴露给调用方。
