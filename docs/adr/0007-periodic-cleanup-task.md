# 定期清理：进程内 asyncio 任务，每天 1 次，同步直调

过期项清理从「仅服务启动时」扩为「启动时 + 每天一次后台任务」。载体是进程内 asyncio 周期任务，`evict_expired` 同步直调（不丢线程池）。

**背景**：服务对外长跑（数周~数月才重启）。原 `lifespan` 启动清（ADR-0004 落地）覆盖不到运行期间的过期项 → 原文（PII）超期留存、音频堆积。两类清理动机不同：原文是 **PII 合规**（必须**主动**扫——不访问的老合同吃不到惰性删除）、音频是**磁盘卫生**（宽松）。500 合同/月量级下，音频稳态 ~25100 条 manifest、原文 ~1500 条。

**决策**：
- **启动清保留**（廉价有益的冗余，堵住「重启→首次定期」之间的窗口）+ **叠加**一个进程内 asyncio 周期任务。
- **每 24h 一次**（启动后周期 `sleep`，不绑墙钟时刻——27ms 无所谓低峰），单任务内依次 `CONTRACT_STORE.evict_expired()`（90 天）+ `cache.evict_expired()`（30 天）。动机不同但同频无害（各自的 TTL 判据在函数内部）。
- 每轮 `try/except` + 记日志，**不中断循环**（崩了下个周期照跑；最坏退化成「只有启动清」）。
- 24h **硬编码** v1，不暴露为环境变量。
- **不加惰性清理**——每天主动定期够，`get`/`put` 里再顺带 evict 是无谓复杂度。

**为什么 evict 同步直调（不丢 `to_thread`）**：实测单次清理 ~27ms（音频 24ms + 原文 3ms，稳态量级 benchmark）。`evict_expired` 是同步函数，在单事件循环里「独占」跑完 = **原子、无竞态**（期间 `get`/`put` 进不来，等于安全）。若丢 `to_thread` 消掉这 27ms，会引入 manifest 跨线程竞态（遍历与删除并发、`_save` 互相覆盖）、需加 `threading.Lock`，得不偿失。**每天 1 次、27ms 低峰阻塞可接受；同步直调是故意的，勿擅自「优化」成 to_thread。**

**代价 / 已知延后优化点**：evict 是 O(manifest)，且 `_save` 每次 `removed>0` 就把**整个** manifest JSON 全量重写——规模增长 N×，阻塞随之 N× 增长。届时（阻塞可感知，如 >100ms）再上分批 evict / 增量 _save / to_thread+锁。当前规模（500 合同/月）下 27ms，YAGNI。

**考虑并否决**：
- **外部 cron / 独立清理进程**：单实例（ADR-0003）下纯粹多余复杂度，且多一个要运维/监控的移动部件；多实例部署时才重新考虑。
- **`to_thread` 消阻塞**：为 27ms 引入 manifest 竞态 + 锁，负收益（见上）。
- **惰性清理为主**：原文 PII 吃不到（没人访问的老合同），不能单独靠它；音频可惰性但主动定期已够。

**修正 ADR-0004**：留存策略（TTL / 判据）不变，补「清理触发」——原文/音频除启动清外，另有每天 1 次的进程内后台定期清理。
