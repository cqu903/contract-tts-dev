# 粤语合同朗读 + 可拖动进度条 — 可行性穿刺设计

- **日期:** 2026-07-25
- **状态:** 设计已评审通过,待写实施计划(writing-plans)
- **相关:** `CONTEXT.md`(本项目能力词汇表)、`probes.ipynb`(Qwen3-TTS 能力边界验证)

---

## 1. 背景与目标

**业务场景:** 客户用浏览器听合同朗读,可自行拖动音频进度条;后台根据拖动到的位置生成后续语音;前后音色须一致。本地部署(M3 Max),粤语,内容可达约 1 小时。

**现状(已验证):** 本项目 `mlx-audio + Qwen3-TTS 1.7B` 在 M3 Max 上能实时(RTF≈0.79)、普通话/英语地道;但**粤语无方言路径**(`CONTEXT.md` 探法 C:`supported_speakers=[]`、`spk_is_dialect={}`),VoiceDesign 的"粤语口音"instruct 也只是"港味音色读粤字"、地道性存疑。

**引擎选型(已调研):** 本地唯一同时满足「真粤语 + voice-clone(解长文音色一致)+ Apple Silicon 可推理 + 支持流式」的是 **GPT-SoVITS**(`yue` 一等语言,有粤语训练集)。CosyVoice2 粤语/流式最强但 Mac 仅 CPU、无 MPS/MLX(GitHub issue #134 仍 open),不采纳。Kokoro(已在 mlx-audio)无粤语音色。

**架构选型(已讨论):** "拖动进度条"是随机访问,必须**分段**而非一条连续流式——进度条需要「位置↔文本」映射,流式生成时未知时长画不出可拖动时间轴。静态/动态内容用**内容寻址缓存**(key=hash(段文本+voice_id))统一处理,**消除"拖动时先判断静态/动态"的分流复杂度**。

**本穿刺目标:** 用最小但完整的环路验证:GPT-SoVITS + 上述架构,在 M3 Max 上能否支撑"拖动进度条、按位置生成、前后音色一致"的体验,并测出关键延迟。

> **这是可行性穿刺(spike),不是生产服务。范围刻意收窄。**

## 2. 范围

**In:**
- 一段合成的书面中文短合同(朗读约 2–3 分钟),用粤语发音朗读。
- 架构:确定性分句 → 内容寻址缓存 → 段内流式生成 → seek→分段映射 → 带可拖动进度条的网页。
- 引擎:GPT-SoVITS(独立 venv,本地 CPU 推理)。
- 音色:固定一段粤语参考音频,每段 voice-clone(跨段一致的机制)。
- 验收:架构跑通 + seek 流畅 + 跨段音色耳听一致 + 冷 seek 首包延迟可测。

**Out(本次不做):**
- 1 小时整篇合同(环路验证即可,扩规模=多分段)。
- 粤语母语级地道性评判(单独后续关卡,go/no-go 另行决定)。
- 认证、多合同管理、真实数据库。
- 自定义音色克隆管理(只用一段固定参考)。
- 段内精确子 seek(seek 吸附段边界即可)。
- 真实时长回填精修进度条(用估值即可)。

## 3. 关键决策(已锁定)

| 决策 | 选择 | 理由 |
|---|---|---|
| 输入文本/发音 | 标准书面中文,粤音朗读 | 真实 HK/GD 场景:合同是书面中文,客户用港式粤音听 |
| 地道性门槛 | 架构优先,地道性后评 | 架构与引擎解耦,粤语不够地道也不白做 |
| 引擎 | GPT-SoVITS(`yue`) | 本地唯一同时满足真粤语+voice-clone+Mac可推理+流式 |
| 集成方式 | 双进程:GPT-SoVITS 独立 venv API + FastAPI 编排 | 避 Python 3.9/3.10 vs 3.12 冲突;引擎可独立升级 |
| 音色来源 | 固定粤语参考音频 voice-clone | clone 优先(无可靠粤语预置);固定参考=任意 seek 顺序同音色 |
| 语料 | 合成书面中文短合同(~2–3min) | 够测分句/seek;不用 1h |

## 4. 架构

```
┌──────────┐  HTTP   ┌────────────────────┐   HTTP    ┌──────────────────┐
│ 浏览器    │───────▶│ FastAPI 后端        │─────────▶│ GPT-SoVITS 引擎   │
│ HTML/JS  │◀───────│ (项目 3.12 venv)    │◀─────────│ (独立 venv,本地)  │
│ +<audio> │ 音频流  │ 分句/缓存/seek映射   │  音频流   │ api_v2.py (CPU)  │
└──────────┘        └────────────────────┘           └──────────────────┘
                            │
                            ▔▔▔▔▔▔▔▔▔▔▔▔▶ 磁盘缓存 cache/<hash>.wav + 清单
```

两个进程 + 磁盘缓存 + 后端托管的静态网页。GPT-SoVITS 在 M3 Max 上走 CPU 推理(RTF≈0.5 量级)。

**一次 seek 的数据流:**
1. 用户拖到 t 秒 → 前端按段索引算出落在第 K 段。
2. `GET /api/segment/{id}/{K}` → 后端查内容寻址缓存。
3. **命中** → 直接流式回放文件(瞬开)。
4. **未命中** → `normalize_for_tts(段文本)`(数字/金额/日期/型号 → 中文)→ 调 GPT-SoVITS 生成,**收齐整段字节后**回传 + 落盘(非 tee;为能回明确错误码)。
5. 前端 `<audio>` 拿到整段 wav 即播;同时后台预热 K+1…K+n。

## 5. 组件

| 组件 | 职责 | 关键点 |
|---|---|---|
| **分句器 segmenter** | 合同文本 → 确定性分段(按 `。！？；`,过长句再按 `，、` 切),每段 `{id, text, est_dur_s}` | **确定性**是缓存键稳定的前提;`est_dur` 按字数×语速估(粤语自然语速 ~3.5–4 字/秒,实测校准) |
| **内容寻址缓存 cache** | key=`hash(归一化段文本 + voice_ref_id)`,磁盘 `cache/<hash>.wav` + manifest.json | 相同文本(静态 boilerplate)跨合同自动复用一个文件 → 免费"预生成" |
| **FastAPI 后端** | 3 个接口 + 托管网页 | 轻量,只做编排 |
| **GPT-SoVITS 适配层** | 对 `api_v2.py` 的薄 HTTP 客户端:`(文本, 固定参考音) → 流式音频字节` | lang 走粤语;固定参考音频保证跨段同音色 |
| **前端** | 进度条 + `<audio>` + 播放/seek/预热 | 纯 HTML/JS,无框架 |

**后端接口:**
- `GET /api/contract/{id}` → 段索引:`[{seg_idx, est_dur_s, cumulative_start_s}]` + 总估时。前端用它画进度条。
- `GET /api/segment/{id}/{seg_idx}` → 该段音频(命中=`FileResponse` 回放文件;未命中=归一化→生成→落盘→`Response`)。引擎失败回 502、其它异常回 500。
- `POST /api/preload/{id}/{seg_idx}`(可选)→ 后台预热后续段。
- `GET /` → 静态网页。

## 6. seek→分段映射 & 进度条(核心)

- 进度条由**预估**每段时长构成 → **音频还没生成就能拖**(连续流式给不了)。
- 映射:拖到 t 秒 → 找 `cumulative_start_s ≤ t < 下一段` 的那一段。
- **seek 吸附到段边界**:拖到一段中间也从头播该段。段很短(~5–10s),"从头读这一句"在合同场景可接受 → 省掉子段内精确 seek 的复杂度。
- **(可选增强)** 段生成后用真实时长回填,精修进度条;穿刺用估值即可。
- **(可选增强)** 段内精确子 seek,后续再做。

## 7. 错误处理

- 引擎未就绪/超时 → 503,前端显示"引擎未就绪"。
- 单段生成失败 → 该段 500,**不污染缓存**,前端可重试/跳过。
- 并发请求同一未命中段 → 按 hash 加锁/"生成中"占位,只生成一次(内容寻址天然去重)。
- 段过长卡住 → 段本就短;引擎停滞则超时报错。

## 8. 测试与验收

- **单元:** 分句器确定性(同文本→同分段)、缓存键稳定性、seek→段映射数学、`est_dur` 合理性。
- **M0 引擎冒烟:** GPT-SoVITS 本地起来,生成一段"书面中文合同文本"的粤语音频,**听起来是粤语即可**(不做母语级地道评判——那是后续关卡);记录 M3 Max 上的 RTF。
- **端到端(M1+M2):** 进度条按估值渲染 → 从头播放跨段连贯 → 拖到中段,首包延迟可接受 → 拖回已播段,瞬开(缓存命中)→ 耳听跨段音色一致。
- **记录指标:** 冷 seek 首包延迟、重复 seek 缓存命中率、RTF、2–3 分钟语料总生成耗时。

## 9. 里程碑(架构优先)

- **M0** 引擎冒烟:GPT-SoVITS 本地跑通 + 一段粤语样本(可识别为粤语)。
- **M1** 分句 + 缓存 + 单段流式接口(CLI 可测)。
- **M2** 网页 + seek + 预热。
- *(后续关卡)* 粤语母语者地道性复核(go/no-go 另行决定)。

## 10. 风险与未决

- **GPT-SoVITS 粤语质量(书面中文+粤音):** M0 仅判"可识别为粤语",地道性推迟。**最大风险:可能像 Qwen3-TTS 那样是"普通话读粤字"的变体** → 若如此,触发降级(普通话/英语或换引擎),但架构不白做。
- **M3 Max CPU 推理性能:** 官方 M4 CPU RTF≈0.53,推算 1 小时约 30 分钟;短段冷 seek 首包需实测。
- **段边界韵律不连贯:** voice-clone 保音色,但段间 cadence 可能重启;拼接处轻 crossfade + 统一语速可缓解。
- **粤语参考音频来源:** 需约 5s 粤语人声;穿刺用公开短样本或用户提供。
- **Python 版本冲突:** GPT-SoVITS 需 3.9/3.10,与项目 3.12 冲突 → 独立 venv 解决(见集成方式)。
